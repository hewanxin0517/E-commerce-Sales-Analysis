# E-commerce-Sales-Analysis
# 电商销售数据多维度交叉分析 (Superstore Dataset)

## 📌 1. 业务背景与假设
假设我们是一家电商公司的分析团队，目标是在不增加额外营销预算的前提下，寻找销售额贡献最大的核心阵地，并识别潜在的交叉销售机会。

## 🛠️ 2. 工具与数据源
* **数据源**：Kaggle 公开数据集 (Superstore Sales)，原始记录约 9,800 条。
* **处理工具**：DBeaver (SQL 数据提取与聚合) + Excel (数据可视化)。

## 🧹 3. 数据清洗与口径说明
* 在导入数据库过程中，剔除了含非法分隔符及关键字段缺失的异常“脏数据”。
* 最终分析基于 1,066,698.62 的有效销售样本展开（约占原始全量的 47%），能够反映结构性占比特征。
* 图表纵轴单位已统一转换为“万”。

## 💡 5. 业务洞察与下一步建议
* **客群与区域**：个人消费者（Consumer）贡献了最大销售份额；西部区域（West）是最大的销售阵地。
* **品类结构**：科技（Technology）略占优势，三大品类销售额分布相对均衡。
* **策略建议**：针对“西部区域 + 个人消费者”，建议推出“买科技产品搭配办公用品享折扣”的交叉销售（Cross-selling）套餐。

## ⚠️ 6. 项目局限性
本数据集缺乏成本、利润、获客渠道及退货率等财务运营字段。因此本次分析仅代表“销售规模”盘面，无法断言某客群“最赚钱”。若接入真实企业数仓，需 `JOIN` 财务表进行深度 ROI 评估。



## 🛠️ 7. 实战踩坑与复盘 (Troubleshooting & Reflections)

在完成这个从“数据获取”到“业务洞察”的全流程中，我经历了从单纯“敲代码”到“理解数据工程”的思维转变。以下是我在本次项目中遇到的核心问题及解决思路：

### 💣 踩坑记录与解决方案 (Troubleshooting)

1. **数据类型不匹配导致中断**
   * **报错现象**：导入 CSV 时，因源数据中布尔值（True/False）被系统自动识别为数值型，报错 `Can't parse numeric value [True]`。
   * **解决思路**：为了保证数据入库的稳定性，在不熟悉DBeaver界面的情况下选择直接回到数据源头（Excel），将 `True/False` 批量替换为 `1/0`，成功绕过了解析陷阱。
2. **“幽灵表”与缓存滞后**
   * **报错现象**：在 DBeaver 中重命名表后，执行 SQL 报错 `Table doesn't exist`（但我明明在左侧导航栏能看到）。
   * **解决思路**：定位为数据库客户端与底层服务端的“缓存未同步”。通过断开连接（Disconnect）并重新连接（Connect），强制刷新底层元数据，解决了该问题。
3. **特殊字符引发的语法危机**
   * **报错现象**：执行带有多词/括号的列名（如 `ML Hardware (linked)`）时报错。
   * **解决思路**：认识到 SQL 语法的严谨性，使用**反引号（\`）**将特殊列名包裹，并养成了不手敲长列名，直接从左侧拖拽字段的习惯。
4. **致命的“笛卡尔积”陷阱**
   * **报错现象**：使用 `JOIN` 连接两张表后计算平均值，发现所有厂商的平均值竟然一模一样。
   * **解决思路**：排查发现是 `JOIN` 时遗漏了 `ON` 连接条件，导致两表发生了全量交叉匹配（数据翻倍）。修复后，深刻理解了 `INNER   JOIN` 和 `LEFT JOIN` 的运行机制。`INNER JOIN` 是只保留两边都匹配得上的数据（交集），`LEFT JOIN`是以左表为核心，不管右表有没有匹配上，左表都必须保留。
5. **数据探查（Data Profiling）发现“隐形丢失”**
   * **现象**：图表做完后，通过agent，Excel图表，sql数据库交叉核对发现所有区域的总和加起来，仅占原始数据集总额的 47%。
   * **解决思路**：通过 `SELECT COUNT(*)` 对比原始行数，定位到是 CSV 文件中的非法换行符/逗号导致部分行在导入时被系统过滤。**这让我意识到，拿到数据的第一步必须是数据探查，而不是直接写代码。**

### 💡 个人认知升级 (Reflections)

1. **从“写代码”到“业务导向”**：一开始我总以为 SQL 语法越复杂越厉害，但通过这个项目我发现，最核心的语法（`GROUP BY`、`CASE WHEN`）就足以解决 80% 的业务问题。**工具只是手段，回答业务问题才是目的。**
2. **敬畏数据口径与局限性**：在初步得出“某客群销售额最高”的结论后，我意识到本数据集缺失“成本”和“退货率”字段，因此不能盲目推断该客群“最赚钱”。于是在报告中明确声明数据边界和局限性。
3. **学会向 AI 借力**：在排错和业务洞察阶段，我尝试将报错信息或初步结论喂给 AI，让 AI 以“业务总监”的视角对我进行拷问，这种“借助 AI 进行压力测试”的方法，极大提升了我的逻辑严密性。同时通过不断完善提示词，个人需求，AI也不断提出可落地实施的的方案，帮助我完成了整个分析项目的落地以及知识面的拓展。
